# Topic registry

The canonical registry of frontend-architecture's placement-rule topics — name, trigger, gist, reference link, and project-initialization scan parameters. [SKILL.md](../SKILL.md) points here instead of enumerating topics inline; [init.md](init.md) and [audit.md](audit.md) read topic enumeration from this table rather than hardcoding a topic count in prose. Adding a topic later touches this file plus its own new reference file — nothing in [plan.md](plan.md)'s, init.md's, or audit.md's own spec text needs to change.

| Topic | Use when… | Gist | Reference | Keyword hints (package.json/lockfile) | File globs |
|---|---|---|---|---|---|
| Component tiering | placing a new shared component | Placement is decided by reuse/coupling scope and composition depth — never by statefulness. Four tiers, `ui` -> `atom` -> `molecules` -> `organisms`, importing downward only. | [component-tiering.md](component-tiering.md) | `storybook`, `@radix-ui/*`, `shadcn`, `class-variance-authority`, `chakra-ui`, `@mui/material`, `tailwind-variants` | `**/ui/**`, `**/atoms/**`, `**/molecules/**`, `**/organisms/**`, `**/components/**` |
| Feature-folder organization | structuring a new feature folder | Global code holds only domain-agnostic infrastructure; anything that knows a feature's shape lives in that feature's own folder, layered in one fixed order. | [feature-folders.md](feature-folders.md) | `nx`, `turbo`, `@nrwl/*` | `**/features/**`, `**/modules/**`, `**/domains/**`, `**/src/pages/**`, `**/app/**` |
| Data/service boundary | wiring a data or service call | A service is a plain, framework-agnostic function that validates its response and throws a typed error on failure; every call is mediated by a query-caching layer. | [data-service-boundary.md](data-service-boundary.md) | `axios`, `ky`, `@tanstack/react-query`, `swr`, `urql`, `@apollo/client`, `trpc`, `@trpc/client`, `zod`, `yup` | `**/services/**`, `**/api/**`, `**/queries/**`, `**/*.service.ts`, `**/*Api.ts` |
| State-management layering | choosing where state should live | Three tiers — server state, local UI state, shared client state — placed at the nearest common ancestor of what shares it; state that must survive a refresh or be bookmarkable syncs to the URL instead. | [state-management.md](state-management.md) | `zustand`, `redux`, `@reduxjs/toolkit`, `jotai`, `recoil`, `mobx`, `valtio`, `nuqs` | `**/store/**`, `**/stores/**`, `**/state/**`, `**/*.store.ts` |
| Page composition & data loading | composing a page or route | A page/route may fetch directly — "thin" means no business logic, not no data — with auth centralized in middleware and a query-mediation layer opt-in per page. | [page-composition.md](page-composition.md) | `next`, `react-router`, `@remix-run/react`, `astro`, `@sveltejs/kit`, `gatsby` | `**/app/**/page.*`, `**/pages/**/*.tsx`, `**/routes/**`, `**/middleware.ts` |
| Forms & schema validation | wiring a form to validation | A feature's schema folder holds two unrelated kinds of schema — data-boundary DTOs and form-input schemas; a hook owns the form instance and wires the schema through a resolver. | [forms-validation.md](forms-validation.md) | `react-hook-form`, `formik`, `@tanstack/react-form`, `@hookform/resolvers`, `zod`, `yup`, `vee-validate` | `**/schema/**`, `**/schemas/**`, `**/*Schema.ts`, `**/*.form.tsx`, `**/forms/**` |

`zod`/`yup` and the schema globs are shared between the data/service-boundary and forms-validation rows — the schema folder holds both DTO and form-input schemas ([forms & schema validation](forms-validation.md#two-purposes-one-folder)); a hit there is classified by what the schema actually validates, not by which row found it.

This registry covers topics only — not the skill's own operating-mode sections (Project-initialization, Audit mode, Plan mode). Those stay SKILL.md prose; they don't have the reference-link/scan-params shape a topic entry does.
